## License result for every row

Each of the 15 rows was individually checked against its own LICENSE-MIT, LICENSE-APACHE and NOTICE, rather than relying on GitHub SPDX metadata. All 15 codebases say MIT OR Apache-2.0. All 14 Craft app/launcher brand licenses found were also read. Source commit, direct per-product license links, release asset list and evidence paths are recorded in storytold-products.json. An adapter should reference the official executable path and upstream capabilities; do not bundle upstream binaries, media or brand assets merely because the code license is permissive.

ArtCraft is an especially material exception: [NOTICE](https://github.com/storytold/artcraft/blob/1f969a9224934a55417daf10359a6fb1458b63f4/NOTICE) excludes Nintendo sound effects, meme images/likenesses, third-party skyboxes, Lumine MMD motion and Mixamo renders from its MIT/Apache grant. Its third-party service marks and the ArtCraft marks are excluded too. This rules out claiming the entire package is freely redistributable.

Craft apps' brand terms (for example [PhotoCraft's brand license](https://github.com/storytold/photocraft/blob/486afd82cce99255e999224bcfe28de00fd766aa/docs/brand/LICENSE-brand.txt)) permit only narrowly contextual unmodified use within the upstream app; modified distributed forks must remove the marks. Fonts/media retain their own licenses and attribution duties. Cloud generation providers, model weights, accounts and service charges require separate review.

## Recommended first real integration

PhotoCraft is the first verification target because its official released desktop/CLI pair exposes scoped document creation, inspection, rendering/save and authenticated live desktop bridging, allowing a small deterministic image workflow without a cloud generation account. This is an integration choice, not a claim of production maturity. VectorCraft is a strong second candidate for SVG/PDF handoff; FilmCraft follows for timeline/OTIO/PNG-sequence handoff. Their self-reported readiness percentages measure different things and should not be ranked as comparable benchmark scores.

The first slice should preserve official command schemas/tools and use thin MCP passthrough or the documented local control bridge. PhotoCraft live mode uses --bridge and a control-token file; most other products use --connect and FigCraft uses --attach. Do not assume one flag or authentication contract for all products. No embedded Python is needed to drive official Rust MCP. If DCC-MCP needs a Python registry service, place it in the shared Runtime rather than creating one interpreter per app.

Concrete acceptance workflow: official provenance/checksum review; task-owned sandboxed instance; DCC-MCP inventory/search/describe/call into upstream tools; create a synthetic image, inspect its layer state, save/render inside the task workspace, read it back, then expose the artifact to one other DCC using the common asset flow. Launcher/Desktop should discover the official app/CLI and present capability/readiness/diagnostics while retaining upstream installation/update authority. Source tests can cover metadata/schema/transport/timeout/auth/root boundaries; only a real upstream process can establish host validation.

PhotoCraft protocol explicitly distinguishes timeout: not run from timeout: no reply in 60s. The latter has an uncertain mutation outcome and requires inspection before retry. Its control/MCP batch is not atomic; earlier effects remain. Keep root capabilities, token-file authentication, error/isError and per-command annotation semantics intact.
